# Megatracker

See [README.md](README.md) for what the app does, the code layout and the release process.
[PRODUCT.md](PRODUCT.md) and [DESIGN.md](DESIGN.md) describe who it is for and how it looks.

## Starting work

`main` is protected: every change goes through a pull request, and force pushes to `main`
are blocked.

1. Run `git fetch origin`, then branch from `origin/main`, not from the local `main` or
   whatever branch is checked out (it may be an unmerged release or feature branch).
2. Make the change, then run `npm test` and `npm run build`.
3. Before opening the pull request, `git fetch origin` and rebase onto `origin/main` again.
4. Push the branch and open the pull request with `gh pr create`. Never commit to `main` or
   push to it directly.

A pull request can only merge once it is up to date with `main` and the **Test and build**
check passes.

## Changelog

- Add a line to `CHANGELOG.md` only for changes players will notice, not for tooling or CI.
- Entries go under `## [Unreleased]`, in a `### Changed` (or `Added` / `Fixed`) group.
- Releases rename `[Unreleased]` to the version number. If one lands while your branch is
  open, your entry merges into the released section without a conflict. After rebasing,
  check the entry is still under `[Unreleased]`. CI fails the pull request if it isn't.
- Don't edit version headings or `package.json`'s version by hand; `npm run release:*` does
  that in its own `release/vX.Y.Z` pull request.

## Code

- `src/data/advances-*.ts`, `calamities-*.ts` and `interactions.ts` are generated by
  `scripts/import-calculator-data.mjs`; don't edit them by hand.
- Game rules live in `src/engine/` as pure functions with Vitest tests. Add or update a test
  there when changing rules logic.
- Check UI changes in the dev server (`npm run dev`), at phone width as well as desktop.
